## Covered contracts

`tests/e2e/access/invitation-lifecycle.spec.ts` issues invitations through `/admin/users` and the real `sendInvitation` server action. Its acceptance case uses `/invitations/{token}` and `accept_tenant_invitation`, then verifies membership, consumed invitation state and second-use denial through fresh actor sessions. Separate cases have passed for duplicate pending invitations, mismatched identity and an expired deadline.

The local runtime does not configure Resend. The invitation dialog always exposes the product-generated link, which is the tested handoff. These cases do not prove email delivery or provider compatibility.

`tests/e2e/access/notification-inbox.spec.ts` inserts each precondition through the recipient's anon-key RLS client. `/admin/dashboard` supplies the tenant-scoped persisted unread list. The root `NotificationsListener` supplies unread toasts and handles **Descartar** by setting `read_at`. The recipient case now waits for its specific Sonner toast before dismissal. A failure case returns HTTP 503 for the real notification update request, verifies that `read_at` stays null, reloads, and requires the toast to appear again. The tenant case inserts the tenant-B row first, then a tenant-A witness, waits for the tenant-A toast, and only then asserts that tenant B stayed absent. This prevents an immediate post-navigation count from passing before the listener fetch runs.

`NotificationsListener` now receives the server-resolved user and active tenant from `app/layout.tsx`. Its initial query includes user-level rows with `tenant_id = null` plus rows for the active tenant. Realtime callbacks apply the same scope before showing a toast. Scope changes cancel pending callbacks and dismiss toast IDs created by the old scope. A failed `read_at` update no longer writes the notification ID to local dismissed storage.

`/notifications` currently renders reminder calendar data. Although `app/notifications/_components/notifications-table.tsx` exists, the page does not render it. This slice does not claim list, read, or delete coverage through that unused component.

## Private setup boundary

`tests/e2e/fixtures/access.ts` only moves an owned invitation deadline into the past. It verifies the tenant, fixture inviter, fixture recipient namespace, and pending status before the service-role update. The owner actor then calls `expire_old_invitations`; the recipient denial and all durable assertions use actor sessions.

The tenant-isolation notification case uses the existing purpose-named permission fixture to make the owner a member of tenant B before that actor inserts its own tenant-B notification. Product RLS still handles the insert and read.
