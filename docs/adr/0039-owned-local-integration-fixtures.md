# ADR 0039: Test-owned actors on an isolated local stack

## Status

Accepted for test infrastructure on 2026-10-17. Runtime verification is recorded in `plans/2026-10-17-isolated-integration/README.md`. This supersedes ADR 0038's manual environment selection and shared authentication setup, while retaining its loopback target checks.

## Context

The former Playwright setup reused one fixed tenant and one auth file, could reset an existing user's password, and ran every test through an owner. Tests mutated shared names and used service-role reads for business assertions. A local hostname alone did not establish that the instance belonged to the tests. Next could also load ordinary development environment files.

The application has separate membership and operational permissions. Membership roles are owner, admin and member. A viewer is a member with read permissions; an editor is a member with an operational role. ADR 0033 intentionally keeps same-tenant UPDATE RLS broader than API edit authorization. Fixtures must preserve that distinction.

## Decision

Use one complete scenario per test attempt. Each owns two UUID tenants, minimally valid obra defaults and lazily created synthetic actors. Retries create new scenarios. Actors use actual password authentication, SSR cookies and anon-key Supabase clients with their own sessions. Their API, page and RLS assertions exercise application behavior. Service role stays inside fixture preparation and cleanup.

Remove shared auth setup and migrate all existing callers in the same change. Public tests use an independent fixture without tenant/auth provisioning. Authenticated tests select actors by business role. Fixture seed operations name their purpose instead of exposing an administrator client to specs.

`scripts/test-integration.mjs` owns a temporary Supabase workdir with a unique project ID, free local ports, unchanged repository migrations, disabled ordinary seed and disabled third-party auth. It creates a separate application snapshot with production proxy/instrumentation and current source changes, excluding `.env*`, caches and local data. Dependencies are shared through a node_modules link. Next runs in that snapshot with an allowlisted environment and local keys generated by the owned stack. No hosted account or existing database is selected.

The runner owns process teardown and stops only its named Supabase project with disposable-volume removal. It verifies that no containers, volumes or networks remain for the project identity, and that the application process, port and temporary source snapshot are gone. It records a secret-free run manifest and uses a separate Playwright artifact directory for each run. Public mode starts only the isolated application. Discovery starts neither app nor database. Direct execution without the owned-run manifest fails with the supported command.

Fixture resource intentions are recorded before creation. Cleanup drains pending setup, closes browser contexts, reconciles resources created by the app, removes storage objects and current restrictive/audited children while their parents exist, then removes users. Auth, profile and Storage absence are checked through readback. Readback errors remain errors; cleanup may not report absence from a failed query. A cleanup failure fails the test and retains recovery identifiers.

SQL disposal belongs to the entire owned stack. Migration 0046 intercepts DELETE on obras, certificates, pending tasks, schedules and calendar events with an unconditional soft delete. A successful DELETE therefore does not establish absence. Deleting a tenant can cause its cascading soft delete to insert an audit row after the tenant is gone, violating the audit tenant foreign key. Fixtures preserve these product triggers and do not delete tenants. Their unique identifiers isolate attempts while residual SQL remains until stack disposal. The lifecycle specification proves that a real obra remains with deleted_at after DELETE, alongside actual auth and Storage cleanup.

Each durable fixture manifest includes kind, runId, projectId, namespace, resource intentions and cleanup errors. Successful runtime cleanup records status `awaiting-stack-disposal` and runtimeCleanup `verified`; failure records `cleanup-failed` and `failed`. A worker that stops early leaves `active` and `pending`. Only the runner, after verifying stack and application disposal, records status `disposed` and disposedAt. It preserves runtimeCleanup and errors, so destroying the stack cannot turn a failed or interrupted fixture cleanup into a passing check. If disposal fails, the manifest retains its pending state and the run fails.

External HTTP transports in the isolated Node process are rejected and browser contexts restrict their network origins. This is a test transport boundary, not an operating-system network sandbox. Provider compatibility remains an explicit separate job.

### OCR transport extension, 2026-10-19

Authenticated runs own an additional loopback HTTP listener with a random token. Tests register synthetic source SHA256/MIME pairs and a Gemini extraction response, optionally preceded by a bounded failure. Unknown bytes, unsupported envelopes and unauthenticated requests fail. The server records byte count, hashes, model path and attempt count without retaining source bytes, prompts or credentials in its evidence.

The test-only network preload validates the matching owned manifest before rewriting the exact HTTPS Gemini generateContent POST fetch to this listener. It preserves the request body and cancellation, removes provider credentials/query data and attaches the local token. All other external HTTP requests remain rejected. The runner writes `starting-app` before spawning Next, and closes the provider listener and verifies its port during teardown. Public runs have no provider listener.

This keeps the application's OCR route, parsing, plan accounting, Storage writes, SQL, lineage and RLS intact without introducing a production endpoint override or paid calls. The older lineage extraction/storage stubs remain useful for their narrower conflict contracts; they are not counted as full extraction proof. Synthetic transport responses cannot establish recognition accuracy or compatibility with the current live provider. Those remain separate, explicitly authorized provider jobs.

The immutable snapshot runs with Next dev/webpack. Authenticated browser contexts pin only the SYNC compilation hash on that owned app's `/_next/webpack-hmr` WebSocket to the initial hash. A captured Chromium initiator stack proved that a later development SYNC hash mismatch called `window.location.reload()` during cold compilation, discarding a template form without any application navigation. The socket stays connected and forwards every other development message. The fixture keeps product APIs, Supabase and business WebSockets unchanged. These runs prove behavior in this isolated development runtime; production-build behavior and performance remain separate checks. See `plans/2026-10-19-deep-document-qa/hmr-runtime.md` for the trace and CDP attachment.

Authenticated test contexts send `Connection: close` for local HTTP. Browser-bound Playwright API contexts otherwise reuse a pooled socket after the preceding browser context closes. Two full/focused runs observed the next obra setup PATCH fail with `ECONNRESET` while the application remained healthy. The checked-in loopback probe demonstrates that cross-context reuse, injects a close on the reused socket, and verifies that the explicit close policy gives each request a fresh connection while preserving browser WebSocket Upgrade. This removes shared transport state between test identities without retrying potentially committed writes. Test retries stay zero. The probe is `plans/2026-10-19-deep-document-qa/http-connection-probe.mjs`; its JSON distinguishes injected failure from the actual runtime observations.

## Alternatives

Worker-owned actors would reduce setup time, but tests change defaults, roles, subscriptions and preferences indirectly. We accept additional setup in exchange for independence without maintaining a second scope policy. A transaction per test cannot cover auth identities, browser sessions or storage bytes. An ordinary local database plus a marker cannot establish exclusive ownership.

A stack per test would isolate global database state more strongly and remove SQL after each attempt, but would repeat migration and service startup for every test. The current suite uses one stack per run with unique tenants and actors per attempt. Tests that mutate global state need a separate run or a transaction that rolls back, as the permission migration specification does. Future resource types that prevent user deletion through restrictive references must fail cleanup explicitly and receive a scoped cleanup implementation.

## Consequences and limits

The supported commands become `npm run test:e2e`, `npm run test:e2e:public` and credential-free discovery. Neither configured user passwords nor `.env.e2e.local` are required. Integration starts from repository migrations and must expose their failures; fixtures must not reorder or repair them to obtain a passing result.

Fixture disposal preserves the production soft-delete and audit triggers. A separately approved repair to historical migration `0123` and new migration `0132` restores ADR 0029; its rationale is recorded in ADRs 0028 and 0029. Execution in this task uses only disposable local data. Runtime evidence must distinguish a discovered spec, a mocked-provider lineage case, a passing real route, and an authenticated journey that actually executed.
